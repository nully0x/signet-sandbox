Signet Sandbox is a one-click private signet environment for the Bitcoin stack. Bitcoind, a custom block signer, electrs, a faucet, and Lightning come up together on one isolated chain. Every endpoint arrives in a single bundle. A timer tears it all down when time is up.

Install

01 / CLI

One binary named signet, installed by a shell script. No repository clone.

$ curl -fsSL https://nully0x.github.io/signet-sandbox/install.sh | sh

LINUX · MACOS x86_64 and arm64. Re-run the same line to upgrade.

  • Docker daemon, running: Docker Desktop, colima, or OrbStack
  • Nothing else. You never manage servers or the platform underneath

First environment

02 / FOUR STEPS
  1. 01
    Bootstrap the local stack

    Prepares the local platform, starts the API, and writes a local identity. Pass the host at this step when other machines must reach the endpoints.

    $ signet bootstrap
$ signet bootstrap --host <host machine ip>
  2. 02
    Provision

    Waits until the environment is ready. The first run premines 101 blocks. --ui opens the dashboard when ready.

    $ signet up --name my-app --ttl 2h --ui
  3. 03
    Read the bundle

    One object holds every endpoint plus the credentials that open it.

    $ signet get my-app --json
  4. 04
    Fund and tear down

    Fund an address from your wallet, or one the node returns with getnewaddress. Remove the environment and its chain when the work is done.

    $ signet fund my-app tb1qexampleaddress --amount 100000
$ signet down my-app

01 / THE BUNDLE

Configuration in. Credentials out.

Names resolve on the server, so scripts never track UUIDs. Disabled components are omitted from the object, not returned as null. Lightning entries are keyed by the instance name you chose.

02 / WHAT AN ENVIRONMENT CONTAINS

Pick the parts you need.

The chain backend always comes up. Everything else is a choice you make at create time, and the choice is recorded in the bundle. Two environments never share a chain or a challenge.

Components, their role, and whether they are always present or optional
Component Role When present
bitcoind Bitcoin Core in signet mode, one chain per environment ALWAYS
block signer BIP325 signer with a per-environment key, 30 second blocks or on demand ALWAYS
electrs Electrum indexer for wallets that track on-chain state OPT-IN
explorer Browser view of blocks, transactions, and addresses OPT-IN
faucet Funds any address with worthless coin from that chain OPT-IN
LND Named Lightning instances, one or many, with REST and gRPC OPT-IN

Lightning instances peer automatically after create. Channels stay manual, because channel liquidity is the thing under test.

03 / WHY THIS EXISTS

Three bad options. One that fits.

01 / REGTEST

Too small

One node. No real peering, no real mempool behaviour, and no sync worth measuring.

02 / PUBLIC TESTNET

Too crowded

Shared with everyone, unreliable under load, and short of coins when you need them.

03 / MAINNET

Too expensive

Real funds and real risk during integration tests. One mistake costs money.

04 / THIS

Private signet

Real proof of work and real chain sync, on a chain that only your key can validate.
